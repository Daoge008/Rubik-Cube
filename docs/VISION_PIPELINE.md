# 视觉识别与连续扫描管线 (Vision Pipeline)

## 零、现状：哪些是真的，哪些还是设计

原始设计文档描述的是 YOLOv8-OBB + `cv::warpPerspective` 的路线。**这条路线没有实现**：
项目没有 OpenCV 依赖，也没有端侧检测模型。当前跑通的是下面这套**固定取景框**方案，
它不依赖模型，纯标准库，可离线测试。

| 环节 | 状态 |
|---|---|
| 相机采集（CameraX imageStream, YUV_420_888） | 已实现 |
| 固定居中 3×3 取景框采样 | 已实现（替代 YOLO-OBB + 透视展开） |
| CIELAB + ΔE94 分类 | 已实现 |
| 白平衡自校准（用首个白面样本） | 已实现（替代"6 个中心块 EMA 锚点"） |
| 8 帧滑动窗口多数表决 | 已实现 |
| 六面拼合 54 色块 | 已实现，**但必须配合面内朝向归一化**（见第三节） |
| YOLO-OBB 倾斜角点检测 | 未实现 |
| solvePnP 姿态 / AR 叠加 | 未实现 |

接 YOLO 时只需替换 `sampleFaceGrid()`：下游只消费九个 Lab 值，不关心中间发生过什么。

## 一、取景框与采样区是同一个矩形

`sampleFaceGrid()` 采样的是**画面中心、边长 = min(正立宽, 正立高) × 0.72 的正方形**，
再切成 3×3。UI 画的引导框用的是同一个比例（`kGuideSideFraction = 0.72`）。

这不是偷懒，是刻意的：**两者几何上恒等，就不需要把 native 的采样区投影到预览控件上**。
那种映射要考虑 letterbox、旋转、缩放，是这类叠加层最常见也最难查的错误来源
（"框看着对齐了，但采的其实是别的地方"）。把框固定住，这一整类 bug 就不存在了。

代价是要求用户把魔方凑到框内。UI 文案明确引导"让魔方填满取景框"。

每格只取**中心 55% 区域**做平均。贴纸外圈紧挨着黑色塑料边框，
把它算进去会把每个平均值都往灰色拖——那正是黄和橙互相认错的原因。

**Dart 侧 `kGuideSideFraction` 与 native 的 `sampleFaceGrid` 默认值必须保持一致。**
设备端自检 `_SyntheticFrame` 也按同一比例生成合成帧，两者一旦漂移，自检会立刻读到黑背景而失败。

## 二、色彩：为什么必须带白平衡

链路：**YUV_420_888 (BT.601 videorange) → sRGB → CIELAB → ΔE94 最近邻**

- 用 **Rec.601** 而不是 Rec.709，因为 CameraX 的 `YUV_420_888` 就是这个矩阵。
  用错矩阵会让饱和色的偏移很明显，而红和绿正是六色里最饱和的两个。
- 分类在 **Lab** 而不是 RGB：同一组 RGB 差值，在两块暗贴上可能是"明显不同"，
  在两块亮贴上可能是"完全相同"。魔方是在现场光下读的，不是标准光源下。

**锚点存在 sRGB 里，不是 Lab 里**——这点很关键。手机相机的白平衡会独立地平移各通道
20% 以上，足以让红橙互换，而"每通道增益"这种校正只有写在 RGB 域才表述得出来。

```
calibrateWhite(measured):
    gain = measured / 245          # 相机把标准白 245 渲染成了 measured
    anchor_expected(i) = anchors[i] * gain

updateAnchor(colour, measured):
    normalized = measured / gain   # 先还原回标准光照域
    anchors[colour] ← 0.85*anchors[colour] + 0.15*normalized
```

两个函数的方向必须一致：`calibrateWhite` 定标"当前光照"，`updateAnchor` 只调"这块贴纸的固有色"。
写反的话，第二帧就会把光照偏差吸进锚点，把刚做的白平衡悄悄抵消掉。

`calibrateWhite` 是**赋值**而不是累加，否则用户重扫时校正会一层层叠加。

首个白面样本要同时满足两个条件才被采纳：三通道和 ≥ 300（够亮），
且被当前锚点判为白。手持第一帧经常对着桌面或斜着的整个魔方，
一个过暗的错误读数会把所有锚点一起缩放，进而毁掉整次扫描。

## 三、面内朝向归一化（没有它，扫描结果根本用不了）

扫描时用户怎么握魔方是不定的，**每个面的九张贴纸到达时的旋转角是未知的**，
而扫描器没法问用户"请精确转 34 度"。直接把六面按 `U R F D L B` 拼接，
得到的字符串几乎必然校验失败——失败信息还会误导人：看起来像某个颜色读错了，
其实每个颜色都对，只是对齐未知。

`FaceAssembler` 枚举 **4⁶ = 4096** 种面内旋转组合，取使最多块合法的那个。

判据必须用「**块颜色集合匹配**」，不能用「相邻贴纸异色」：

> 一个实体魔方恰好有 12 种棱颜色对和 8 种角颜色三元组，且每种各出现一次。
> 只检查"棱的两贴纸不同"远远不够——把某个面转到错误朝向，通常**仍然**能让相邻贴纸互异，
> 它只是把块重新涂色了。那样会出现"评分满分，但描述的是另一个魔方"。

所以评分是：读出的颜色组合必须**落在真实颜色集合里，且不被复用**。

- 遍历按**混合进制递增序**（code 从 0 到 4095），保证多个候选同分时结果与容器迭代顺序无关
  ——否则同一份扫描在不同 STL 实现下会给出不同答案（这个坑在求解器里踩过一次）。
- 遇到第一个满分且 `validate` 通过的就返回；都不通过时返回最高分并附错误，
  **分数本身就是诊断**：20 分但校验失败 = 几何对齐对了，但块不可能，指向颜色误读。

## 四、多帧表决

单帧永不采信：手持会抖、对焦会来回拉、一帧坏数据锁进状态就再也发现不了。
一个面要在一整窗（8 帧）里九格都拿到 ≥6 票才锁定。帧按**中心格颜色**分桶
——中心格是最大的纯色区域，读取最稳，也是标识"这是哪个物理面"的依据。

帧率在 Dart 侧节流到 ~11fps。相机给 30fps，但表决用不到那么多，
全速跑只是让手机发热。

## 五、可观测性

`NativeDetectionResult` 末尾携带扫描遥测：`faceFrameCount` / `windowSize` /
`ambiguousCells` / `assemblyState` / `assemblyScore`。

- `faceFrameCount` 让 UI 能显示"正在稳定"的进度条——没有它，用户无法区分
  "手别动"和"它压根没检测到"。
- `ambiguousCells` 是最近邻与次近邻的距离比，越接近 1 越含糊。
  UI 据此提示"靠近一点或调亮光线"，而不是让用户对着一个沉默的界面猜。
- 字段追加在结构**末尾**而不是穿插在中间，这样即使某一侧忘了同步，
  前面的字段偏移仍然是对的。

## 六、怎么测

相机无法在构建机上复现，但"相机看到的就是这些像素"只是一个数组，
所以**像素之后的每一环都能精确验证**（`tools/native_tests/engine_test.cpp`）：

1. **合成帧分类**：用与锚点刻意不同的贴纸色渲染 3×3，
   验证分类正确——喂锚点本身只能证明查表能用，说明不了真实魔方和真实相机。
2. **传感器旋转**：同一组颜色分别以 0° / 90° 读入。取景框居中，两者都必须落在贴纸上；
   旋转映射写错就会读到黑背景，九格一起变暗。
   （注意期望值也要跟着转：转了 90° 的画面，看到的本来就是转过 90° 的那一面。）
3. **白平衡**：暖偏色下先确认**会出错**（否则这个测试什么也没证明），
   再确认校准后错误归零。实测：暖偏色 3/9 格误判 → 白平衡后 0/9。
4. **朝向归一化**：随机打乱态切六面、每面随机旋转，要求 60/60 全部还原成**等价**的魔方。
   等价性用「块颜色组合的多重集」比较——整体旋转会移动块但不会重新涂色，
   而拼错的面恰好就是在重新涂色。
5. **误读必须被拦下**：互换一面的两个贴纸，要求组装失败且评分下降。

设备端另有一条**完全不需要相机**的端到端自检（`native_selftest.dart` 的
`_SyntheticFrame`）：合成 I420 帧喂进 `process_camera_frame_yuv`，走完采样 →
分类 → 表决 → 拼合，验证 arm64 上整条视觉链路可用。这条在真机日志里可直接读到。
