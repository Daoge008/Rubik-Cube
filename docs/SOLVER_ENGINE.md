# 求解算法引擎与数学校验 (Solver Engine)

## 一、54-Facelet 展开与守恒定律

`cube_model.hpp` 维护 `cornerFacelet` / `edgeFacelet` 双向映射（Kociemba 标准布局），
`validate()` 逐项校验：

- 颜色计数（每种颜色恰好 9 块）
- 角块自转守恒 `sum(twist) % 3 == 0`
- 棱块翻转守恒 `sum(flip) % 2 == 0`
- 置换奇偶性守恒（角块逆序数奇偶 == 棱块逆序数奇偶）
- 每种角块/棱块组合唯一（禁止重复块）

## 二、走子引擎（`move_engine.hpp`）

18 个动作表（`U/U2/U'/R/...`，索引用 `face * 3 + (amount - 1)`，面序 `U R F D L B`）
由「拧一个还原态魔方」自举生成，不手写置换表，避免抄错。
`parseSequence` / `sequenceToString` / `inverseMove` / `invertSequence` 提供记号层。

## 三、Kociemba 两阶段最少步（`kociemba_solver.hpp`）

坐标：twist(2187)、flip(2048)、slice(495)、slicePerm(24)、cornerPerm(40320)、edgePerm(40320)。
两阶段剪枝表由反向 BFS 构建，IDA* 先把状态降到群 H，再在 H 内搜到还原态。

实测（宿主侧 200 例随机 25 步打乱）：**200/200 全还原，步数 18 / 20.8 / 23（min/avg/max），
平均 48 ms，剪枝表 5.55 MB。**

两个关键实现要点，写错会静默产出错解：

- `sliceCoord` 的索引 0 必须对应**还原态**，因此 mask 需按降序枚举，否则整张剪枝表以错误目标点构建；
- phase 1 到达子群后**必须**继续跑 phase 2 —— 子群 ≠ 终点。

## 四、CFOP 教学流水线（`cfop_pipeline.hpp` + `last_layer_algorithms.hpp`）

九阶段：Cross → F2L ×4 → OLL 棱翻色 → OLL 角翻色 → PLL 角归位 → PLL 棱归位。

### 4.1 十字与 F2L：带精确启发式的 IDA*

每个阶段用其相关块组的**松弛距离表**（`subproblem_tables.hpp` 的 `PieceGroupTable`）取 max 作为
可采纳启发式。表是「1–4 个块的 (位置, 朝向) 坐标」上的精确距离，用多源反向 BFS 构建，
并用 `consistent()` 过滤同位置冲突的种子（否则多源 BFS 会被污染，距离偏小）。

搜索的候选步集只用「**除 D 面以外的所有面**」。这一点容易写错：曾经按槽位收窄成
「U + 该槽位两个侧面」（看起来更像教科书 F2L），结果角块埋在对面槽位时根本取不出来，
1/3 的 F2L 搜索超时后静默降级到无约束搜索，平均耗时 5 秒。

### 4.2 顶层：命名公式链，不是原始搜索

顶层**不**用 IDA*。原因是教学需求：最优顶层解是一串混合面的 18 步「乱码」，没人会背，
也无法讲解。改为在**标准 2-Look OLL / PLL 公式集**上做搜索：

- 生成元 = U 对齐转动 + 本阶段自己的公式；
- 目标测试与原始搜索**完全同一个** `stageReached()`，两者对「阶段完成」的定义不可能分歧；
- 用**一致代价搜索（Dijkstra，按步数）**而非「最少公式数」BFS：一条 17 步 Y 型公式胜过
  T 型 + A 型两条，而单纯转顶层又胜过一切 —— 这正是人挑公式的方式。

公式分四组，每组对该子问题必须**完备**（存在缺口时阶段会静默退化成原始搜索，教学价值归零）：

| 组 | 公式 | 覆盖 |
|---|---|---|
| OLL 棱 | 直线型 `F R U R' U' F'`、直角型 `F U R U' R' F'` | 8 种合法棱翻转模式 |
| OLL 角 | Sune `R U R' U R U2 R'`、Anti-Sune `R U2 R' U' R U' R'` | 27 种合法角自转模式 |
| PLL 角 | Aa 三循环、Ab（Aa 取逆）、T 型（相邻角互换）、Y 型（对角角互换） | 全部 24 种角排列 |
| PLL 棱 | Ua、Ub（互为逆三循环）、H（对棱互换） | 12 种偶棱排列 |

角块一组必须同时含**偶**（三循环）与**奇**（互换）生成元：纯偶生成元永远凑不出一次对换。
棱块一组只需偶排列，因为角块归位后剩下的棱排列保证为偶。

### 4.3 实测结果（宿主侧 40 例随机 25 步打乱）

| 指标 | 重构前 | 重构后 |
|---|---|---|
| 全还原 | 40/40 | 40/40 |
| 总步数 min/avg/max | 49 / 59.0 / 71 | 50 / 74.0 / 94 |
| 最长单阶段 | 31 步（两阶段兜底） | 24 步（2 条公式） |
| 平均耗时 | 5052 ms | **30 ms** |
| 退化为两阶段算法 | 4/25 例 | **0/40 例** |
| 顶层阶段 | IDA* 乱序 | **命名公式（tier 0）** |

阶段耗时分布（25 例随机打乱）：Cross 0 ms、F2L ×4 合计约 46 ms、
顶层四阶段各 0.1 ms。

## 五、宿主侧测试（`tools/native_tests/`）

`run_tests.bat` 用 MSVC 直接编译 `engine_test.cpp`，与 Android 库**共用同一份头文件**，
所以在电脑上全绿就意味着 C++ 引擎在进手机之前算术是对的。

覆盖：facelet ↔ cubie 往返、单步手推校验、群阶（R,U 阶 105、sexy move 阶 6）、
非法态拒绝、坐标合法性、Kociemba 200 例、phase2 隔离、phase1 分组、
**顶层公式表逐条效果打印 + 四组公式完备性穷举（335 个合法状态）**、CFOP 40 例。

`probe.bat` 是诊断工具（非测试），按阶段输出耗时、级联层级与阶段长度直方图。

顶层完备性穷举是这个模块最有价值的一条测试：公式集缺口不会让任何东西崩溃，
也不会让端到端用例失败 —— 它只会让某个阶段悄悄退回原始搜索，给用户一段 25 步乱码。
只有把每个子问题的合法状态空间**枚举穷尽**，才能知道「每阶段一两条可背公式」这个承诺
对任意打乱都成立，而不只是对抽样到的那些成立。

## 六、跨平台确定性（踩过的坑）

**同一份代码、同一个打乱态，电脑算出 9 个阶段 89 步，手机算出 8 个阶段 79 步。**
两边都是**正确**的解（都能还原），但教学 App 不能这样：同一个魔方每次给出不同的指导，
用户会以为哪里出错了。

排查路径（每一步都靠取证，不靠猜）：

1. **先排除「时间预算」**。阶段搜索按墙钟时间截断，速度差异会导致降级到不同 tier。
   写 `budget_probe.cpp` 把预算从 0.02 s 调到 1000 s，电脑结果**完全不变** → 不是超时。
2. **再排除「降级」**。把每个阶段的 tier 通过 JSON 暴露到设备端（`stageTier` 字段），
   逐项对比：设备与电脑的 tier **完全一致**（Cross t2、F2L 全 t1、顶层全 t0）。
   → 不是走了不同的搜索分支。
3. **于是只剩下一种可能**：走的是同一条逻辑、同一个 tier，结果却不同 —— 差异必在
   那条逻辑内部与 STL 实现相关的地方上。定位到顶层链搜索的优先队列。

**根因**：Dijkstra 用的是 `std::push_heap` / `std::pop_heap`，比较器只比 `cost`：

```cpp
const auto later = [&nodes](int a, int b) { return nodes[a].cost > nodes[b].cost; };
```

两条链**未简化总步数相同**时，它们是堆里的**等价元素**，`std::pop_heap` 对等价元素的
顺序**不做任何保证**。MSVC 的 STL 与 Android 用的 libc++ 在这里行为不同，弹出的链就不同。
而不同的链**简化后长度可以不一样**（15 步 vs 16 步）—— 差异就是这么来的。

**修复**：把比较器补成全序，用插入顺序打破平局。

```cpp
const auto later = [&nodes](int a, int b) {
    if (nodes[a].cost != nodes[b].cost) return nodes[a].cost > nodes[b].cost;
    return a > b;   // 全序 -> 堆形态唯一 -> 各平台一致
};
```

插入顺序本身是确定的（生成元按固定顺序遍历），所以比较器变成全序后，堆的每一步比较
都有唯一答案，结果与 STL 实现无关。

**顺带修掉**同一函数里的 `best[packState(node.state)]`：`std::map::operator[]` 在 key
缺失时会**插入一个 0 值条目**，随后每次访问都会显得「更旧」而被剪掉。改用 `find`。

**教训**：这类 bug 在单平台上**永远测不出来** —— 电脑上全绿、手机上也全绿，只有把两端
同一个输入的结果摆在一起对比才会暴露。所以设备端自检保留了这组固定向量，专门做这件事。

## 七、设备端自检（`lib/core/native_bridge/native_selftest.dart`）

App 首页底部的状态条会跑一套真机自检，并且**把结果镜像到 logcat**，所以不看屏幕、
只用 `adb logcat -s flutter` 就能确认一台设备上的构建是否可信。

自检刻意使用**打乱态**而不是已还原态：已还原态在两个求解器里都走 trivial 分支，
剪枝表全错也能通过。

| 检查项 | 抓什么 |
|---|---|
| 库 / 管线句柄 | FFI 是否真的接上（历史上出现过「句柄从未创建、所有调用静默失效」） |
| validate 正反两向 | 非法态必须被**拒绝**，否则校验器形同虚设 |
| solve(已还原) | 正确识别 SOLVED |
| 冷启动（含建表） | 首次求解的表构建延迟 |
| Kociemba 解长度 vs 电脑 | 8 个固定打乱态，跨架构一致性 |
| CFOP 阶段划分 vs 电脑 | 阶段数、每阶段步数、**每阶段 tier** |
| 教学字段完整 | 顶层阶段必须带算法名与讲解 |

固定向量由 `tools/native_tests/gen_vectors.cpp` 生成，同时在注释里打印电脑端
的阶段分解（含 tier），可以直接和设备端日志逐行 diff。

**实测数据**（小米 2410DPN6CC / arm64）：冷启动 154 ms、Kociemba 平均 34 ms、
CFOP 平均 152 ms（含首次建表）。手机并不慢，不需要为性能做 isolate。
